# 招聘信息聚合：原型范围与页面清单

版本：v0.3，2026-10-29。状态：原型评审基线；已据此提供 [可点击原型 v1.0](交互原型使用与验收.md)。已确认普通用户与 V1/V2/V3 每日额度、小程序微信支付、按岗位详情计次及同一岗位可重复查看；具体计费边界见第 11 节。

关联文档：[会员与售后规则](会员与售后规则.md)。其中区分已确认、建议基线与待定事项，并补齐 30 天服务方案、续费、独立补偿额度、退款、账号关联及验收场景。交易细则以该规则表为准，未确认方案不作为正式销售承诺。

## 1. 产品与范围

为普通用户及付费会员集中提供可筛选、可追溯、定期核验的招聘信息。普通用户每日可新查看 1 个岗位详情，V1/V2/V3 每日分别为 20/100/200 个，通过小程序微信支付购买会员。后台每日采集指定来源，使用 AI 辅助抽取、分类与摘要，经规则校验、去重和必要的人工审核后展示。

将用户的“Web 后端”暂理解为 Web 管理后台。结合先前的网站需求，产品包含 C 端网站、微信小程序、Web 管理后台三种使用界面。若用户只需要后台与小程序，可移除 C 端网站，不改变岗位业务模型。

两种 C 端共用岗位、筛选、收藏和信息状态规则，采用适合各端的布局。三种界面不代表需要拆成三个后端服务；现有简单分层工程可继续承载业务。

默认先覆盖国内岗位；岗位数据保留社招、校招、实习类型。第一批采集来源优先服务哪类用户尚未确定，不把样例企业或职位当作实际已接入来源。

P0 为第一版完整可用流程，P1 为后续增强。原型展示的自动化、推送等能力不等于已经接入真实服务。

## 2. 用户与核心流程

### 求职者

免登录浏览岗位摘要列表 → 免费搜索及筛选 → 点击岗位详情 → 登录并核验是否已解锁 → 已解锁直接查看；首次解锁核验每日剩余额度 → 解锁成功后查看完整详情、来源与投递指引。

额度不足 → 查看会员等级与套餐 → 小程序确认订单 → 支付 → 服务端确认付款与权益发放 → 回到原岗位，仍需首次解锁时扣次。已查看的同一岗位可重复查看，不因返回、刷新或会员到期再次收费；这一跨日免费回看的边界为对用户表述的当前解释。

登录后可收藏岗位或查看已解锁记录；收藏本身不解锁岗位。遇到错误可以提交反馈。会员价格、有效期及升级换档规则待确认。

订阅条件及提醒为 P1。提醒渠道和小程序的原站访问方式应在实现前核验平台能力；原型中不得将不可用按钮表现为已成功投递或已发送通知。

### 运营管理员

配置来源及计划 → 自动或手动发起采集 → 查看任务与失败记录 → AI 抽取、规则校验与去重 → 异常人工审核 → 发布岗位 → 周期核验与更新 → 处理用户反馈。

后台第一版以管理员、运营人员的工作任务区分界面；复杂的角色权限配置后置，不先建立庞大权限系统。

### 小程序导航

第一版底部采用“职位 / 收藏 / 我的”三个入口。搜索结果、岗位、企业详情从列表进入。订阅与消息放入 P1，避免第一版出现没有实际内容的导航入口。

筛选通过抽屉或底部面板，支持重置、确认、已选数量；多选项必须注明匹配逻辑。企业行业与岗位类别分开，地区至少区分工作地点和远程安排。

### 网站导航

顶部提供职位搜索、收藏、会员中心、个人入口及今日剩余额度；列表采用筛选区与结果区，岗位详情支持从结果进入并返回原条件。窄屏布局适配手机，布局不机械复制小程序。

## 6. 岗位字段与展示规则

| 字段组 | 内容与约定 |
| --- | --- |
| 标识与追溯 | 内部岗位 ID、来源、原站岗位 ID、原始 URL、投递 URL、原文快照及内容摘要哈希 |
| 企业与分类 | 企业名称及标识、企业行业、岗位类别、岗位名称、社招/校招/实习类型 |
| 筛选字段 | 原文经验要求及标准化范围、学历、工作省市/多地点、远程安排、技能标签 |
| 薪资 | 原文薪资、可核实的上下限、币种、计薪周期、薪数；缺失或不可比时不混在统一范围筛选中 |
| 时间 | 来源发布时间、来源更新时间、首次收录时间、最后成功看到时间、最后核验时间、明确截止时间；来源未给出的时间留空 |
| 内容 | 原始职责和要求、明确标识的 AI 摘要、抽取规则/模型版本、校验问题及必要证据 |
| 运营 | 发布状态、招聘状态、最近处理人、处理记录；去重关联不同来源而非直接丢掉来源记录 |

数据原则：未知不自动补成确定值；AI 摘要不替代原始要求；“AI 推断”不伪装为来源明确披露的信息。

“今日新增”应区分首次收录与来源真实新发布；抓取时间不能当作岗位发布日期。

## 7. 状态设计

三个维度分别管理，避免把采集、运营、招聘状态混成一个字段：

- 处理状态：待抽取、处理中、处理成功、处理失败、待人工审核。
- 发布状态：草稿、已发布、已隐藏、已驳回。
- 招聘状态：在招、待核验、已结束、未知。

只有已发布且符合展示策略的岗位进入公共列表；默认列表展示在招岗位，待核验岗位按产品规则单独标识。已结束岗位退出默认结果，但收藏和原链接进入时保留结束状态说明。

采集超时、限流、单次请求失败不能直接判定岗位结束。结束判断需保留来源状态、明确截止时间或其他核验依据。抓取成功也只表示来源页面可读，不代表已保证岗位真实有效。

相同源岗位优先按来源与原站 ID 更新；跨来源重复结合企业、职位、地点等证据判断，不能仅凭岗位名称自动合并不同岗位。

## 8. 原型必须覆盖的交互与异常状态

- 加载中、无数据、筛选无结果、请求失败与重试。
- 组合条件生效、重置、取消、返回列表后保留搜索与滚动上下文。
- 未登录解锁详情或收藏、登录成功返回、取消登录返回、收藏重复点击和失败回退。
- 岗位在招、待核验、结束；缺少薪资、缺少日期、原文与摘要的区分。
- 原站投递入口可用、受限、失败；不得将点击链接当作完成投递。
- 反馈提交成功、校验失败、提交失败；后台可定位到具体岗位。
- 来源健康、暂停、失败、从未执行；启停后的效果明确。
- AI 抽取异常、缺字段、疑似重复、人工修正、保存失败与未保存离开提示。
- 后台发布/隐藏/重试的结果反馈，重复执行的处理以及任务无记录状态。
- 图表和演示岗位均使用清晰的样例数据说明，不宣称接入了尚未接入的企业。
- 未解锁提示、首次查看扣次、已解锁跨日回看、额度耗尽、跨日额度更新、会员到期、普通用户开通会员后重新计算剩余、同级续费、跨级暂不可购买、补偿额度使用与到期。
- 支付取消/失败/确认中、已付款未开通、重复点击、重复通知、退款处理中/失败/成功；已扣款不诱导用户重复支付。

## 9. 原型与开发的对应方式

页面使用稳定 ID（Cxx/Axx）。每个页面标注入口、出口、字段、操作、状态及 P0/P1；关键交互提供可点击路径。网站、小程序、后台的相同岗位样例使用一致数据。

原型评审后，再形成页面 → 功能 → 接口 → 数据字段 → 验收点的映射。前端开发和后端实现以确认后的版本为准，变更记录不覆盖历史结论。

建议先绘制五条完整路径：

1. 求职者：条件筛选 → 登录 → 首次解锁扣次 → 岗位详情 → 原站投递指引。
2. 用户留存：已查看/收藏岗位 → 再次查看不扣次 → 岗位状态变化。
3. 数据运营：配置来源 → 采集结果 → 异常审核 → 发布 → C 端出现。
4. 数据纠错：用户反馈 → 后台处理 → 修正或核验 → C 端状态同步。
5. 会员交易：额度耗尽 → 会员中心 → 小程序确认订单与支付 → 服务端确认 → 权益到账 → 返回原岗位解锁；同时演示取消、延迟和售后路径。

第一版先完成以上路径，再扩展订阅、通知、企业关注和统计报表。

## 11. 会员与详情查看规则

### 已确认需求

| 用户等级 | 每日可首次解锁岗位数 | 购买方式 |
| --- | --- | --- |
| 普通用户 | 1 | 免费 |
| V1 | 20 | 小程序内支付购买会员 |
| V2 | 100 | 小程序内支付购买会员 |
| V3 | 200 | 小程序内支付购买会员 |

用户已确认按“查看一个岗位详情”计次，而非按条件搜索计次，并希望可重复查看同一岗位。

### 当前原型默认解释，待评审

1. 搜索、筛选、翻页、岗位摘要、企业简介、收藏操作均不扣次；完整详情和投递来源受岗位解锁权益控制。
2. 登录用户首次成功解锁一个有效岗位扣 1 次，同时生成用户与统一岗位 ID 的解锁记录。已解锁岗位再次查看永久不重复扣次，含跨日与会员到期后的回看；“永久”仅指不再消耗额度，内容展示仍受岗位结束、删除及保留政策影响。
3. 原型首次打开未解锁详情先展示摘要，按钮明确标注“查看完整岗位，消耗 1 次”；首次成功后进入完整详情。按钮上或旁边显示剩余额度。已经解锁的按钮文案为“再次查看，不扣次数”。
4. 每日额度按 Asia/Shanghai 自然日计算，不累积、不结转。V1 的 20 次是当日总上限，不额外叠加普通用户的 1 次。
5. 同一用户网站及小程序共享会员、每日额度和岗位解锁记录；实现前需确定可靠的账号绑定方式，不按设备分配新额度。
6. 用户与岗位唯一权益记录、用户与日期额度记录共同保障原子扣次和去重。并发点击、刷新或多端同时打开同一岗位，最多生成一条解锁与一次扣次；不同岗位也不能并发突破限额。
7. 不存在、已隐藏、未发布或不允许新解锁的结束岗位、请求失败及详情不可用不扣次；查询参数校验失败不扣次。已结束但已解锁岗位可展示归档或状态说明。
8. 当天普通用户已用 1 次后购买 V1，按总上限 20 计算，剩余 19；开通会员不清空已用计数。当天重复续费也不能刷新额度。会员到期回归普通用户时，剩余为 max(0, 1 - 当日已用)。
9. 新会员在服务端核实付款并成功发放权益后生效；同级续费延长有效期，不重复重置每日次数。建议首期采用 30 天服务、同级续费与到期后选档，中途跨级暂不开放，具体规则及确认状态见《会员与售后规则》。
10. 不同来源归并为同一个统一岗位后应共用解锁权益；同岗位正文正常更新不再次扣次。新岗位重新发布是否视为新的岗位，需要明确岗位 ID 和去重策略，不能随意换 ID 再次扣次。
11. 列表、企业页、分享直达、收藏、历史入口及接口响应统一执行权限规则，不能仅用前端遮罩隐藏已经返回的完整内容。
12. 按次收费不代表每次查询调用 AI；AI 负责后台数据加工，会员计次是读取现有岗位详情的业务权益。
13. 基础日额度与售后补偿额度分别记账。建议经核实的错误解锁每事件补偿 1 次、有效 7 天，优先消费最早到期补偿，再使用基础日额度；页面分别展示余额。该方案尚待确认，完整边界见《会员与售后规则》。

## 12. 支付、权益与售后闭环

仅增加原型及需求，当前尚未接入任何真实支付、创建真实商户、扣款或发放生产会员。

原型流程：登录 → 选择已上架套餐 → 查看订单金额、期限和每日额度 → 确认服务及售后说明 → 创建业务订单 → 调用实际获准的支付渠道 → 服务端确认付款 → 幂等发放会员 → 刷新权益 → 返回待查看岗位。

支付与权益是独立状态：

- 业务支付状态：待支付、已支付、已关闭；退款另行记录处理中、成功或失败及退款金额，保留原交易已支付事实。
- 权益发放状态：未发放、发放中、已发放、发放失败待补偿、已按售后规则调整。
- 客户端取消不等于服务端关单；支付回调延迟不等于付款失败。原型提供“确认中/刷新订单状态”，避免重复下单。

实现要求：套餐金额由服务端读取，订单固化套餐版本、价格、期限和额度；支付回调或查单需验签并核对商户、订单、金额及币种；同一笔交易重复通知只发放一次。支付成功但发放失败可自动补偿和后台核实补发，不让用户重新付款。后台对账支持识别已支付未开通等异常。

退款须区分用户申请、人工处理、渠道实际成功及权益调整；未确认成功不能展示“已退款”。不能简单将用户所有会员清空，要关联具体订单发放的权益。《会员与售后规则》提出按订单服务段调整、保留其他订单剩余时长与既有解锁的建议方案；已使用服务退款的金额及最终政策尚待确认。

### 接入核验结论与待办

- 普通小程序支付的官方接入文档列明小程序认证、商户号支付权限与 AppID 绑定要求。这并不自动证明本产品的信息查询会员可以使用普通小程序支付。
- 本产品售卖的是信息查询权益，需要在实现前核验实际经营类目、普通/虚拟支付的适用产品、账号开放能力及 iOS 等系统差异。此次未成功读取微信虚拟支付官方页面，不能据旧资料断言 iOS 一律禁止或直接支持普通微信支付。
- 原型保留“当前环境暂不支持购买”的能力状态；具体实现遵循获准渠道。价格、支付渠道费率、到账周期和退款方式尚未确定，不虚构展示为正式承诺。
