# 会员与售后规则

版本：v0.1 · 2026-10-29 · 用途：原型设计与后续开发的业务基线草案。

关联：[原型范围与页面清单](招聘信息聚合-原型范围与页面清单.md)。页面编号沿用 Cxx（用户端）和 Axx（管理后台）。

## 1. 决策状态

“已确认”来自用户明确要求；“建议基线”是为完成可评审原型提出的具体方案，尚未成为正式销售条款；“待定”需要经营或接入信息才能确定。用户同意补充规则文档，不等于已经批准所有价格、期限和售后细则。

| 决策 ID | 事项 | 状态 | 规则 |
| --- | --- | --- | --- |
| D01 | 普通用户每日额度 | 已确认 | 每日新查看 1 个岗位详情 |
| D02 | V1 / V2 / V3 | 已确认 | 每日新查看分别为 20 / 100 / 200 个 |
| D03 | 扣次单位 | 已确认 | 查看岗位详情，非条件搜索 |
| D04 | 同岗位回看 | 已确认需求，边界按建议基线 | 同一岗位可重复查看；建议跨日、会员到期后也不再次扣次 |
| D05 | 购买入口 | 已确认意图，渠道能力待核验 | 小程序内微信支付开通会员；实际普通/虚拟支付产品及各系统可用性待确认 |
| D06 | 会员期限 | 建议基线 | 第一版仅 30 天包，每份有效期为连续 30 × 24 小时；页面写“30 天”，避免与自然月混淆 |
| D07 | 各等级价格 | 待定 | V1/V2/V3 分别配置；原型显示“价格待定”，真实销售前必须设置并确认 |
| D08 | 首购与续费 | 建议基线 | 首次开通、同级续费、完全到期后重新选档；无自动续费 |
| D09 | 中途升降级 | 建议基线 | 第一版不开放补差价、跨级续费或预约换档；原型明确原因，避免扣款后才提示不支持 |
| D10 | 每日额度刷新 | 建议基线 | Asia/Shanghai 自然日 00:00 换日，不结转；各档为总上限，不叠加普通用户额度 |
| D11 | 账号共用 | 建议基线 | 网站与小程序使用同一内部用户，统一会员、额度、收藏及解锁记录 |
| D12 | 数据错误补偿 | 建议基线 | 经核实的无效解锁发放独立补偿额度；每条解锁事件最多补偿一次 |
| D13 | 退款政策 | 建议基线，销售前需确认 | 未开始的整份服务支持申请全额退款；已开始服务通过售后处理，不在原型写成一律不可退款 |
| D14 | 自动持续提醒 | P1 | 条件订阅与推送不作为第一版已交付的收费权益 |

## 2. 用户购买的服务

会员提供的是在有效期内每日解锁更多招聘信息的权限。平台通过来源整理、字段标准化、去重、定期核验及纠错提高信息使用价值；不承诺招聘成功、面试机会或录用结果。

岗位卡片公开显示公司、名称、工作地点、经验、学历、薪资披露情况、来源名称、核验时间和已解锁状态。完整职责要求、详细摘要、原始来源入口及投递指引在解锁后展示。搜索、筛选、翻页和收藏不消耗额度；收藏不会自动解锁。

普通用户每日 1 次作为当前产品基线。新人赠送额度、额外会员功能均未确认，不自动加入权益对比。20/100/200 的分档需要用真实使用和付费数据验证，不能仅凭规则表认为商业模式已验证。

## 3. 首次解锁与重复查看

| 场景 | 结果 |
| --- | --- |
| 游客点击完整详情 | 引导登录并保留原岗位；未登录不创建扣次记录 |
| 首次查看有效且已发布的岗位 | 用户明确点击“查看完整岗位，消耗 1 次”，成功后扣次并生成解锁记录 |
| 已解锁岗位再次打开 | 无论当日、跨日或会员到期，均不再次扣次 |
| 无剩余额度 | 展示额度不足和会员入口；不返回完整受限内容 |
| 不存在、隐藏、未发布或已确定结束的岗位 | 不允许新付费解锁，不扣次；已解锁用户可看到状态说明或允许保留的归档 |
| 业务处理失败 | 不形成扣次；已预占的额度释放 |
| 服务端已完成解锁但网络响应丢失 | 重试直接取回同一解锁结果，不再次扣次；不能同时无条件返额又保留一次新扣次 |
| 多来源收录相同岗位 | 使用统一岗位标识，共用解锁权益；合并发现重复扣次时进入补偿流程 |
| 同岗位正常更新 | 更新资料并标记时间，既有解锁仍然有效；不能通过改 ID 重复收费 |

“回看不扣次”不是无限期保存任何原始内容的承诺。来源删除、岗位结束、需要撤下内容时保留可用的状态说明；已经撤下的内容不会为兑现回看而重新发布。具体内容保留期限为待定事项。

同一用户与统一岗位最多一条有效解锁关系；每次扣次要关联唯一的解锁业务事件。客户端禁用按钮只是体验措施，并发控制与权限核验由服务端统一执行，覆盖列表、企业页、收藏、分享直达等所有入口。

## 4. 每日额度与独立补偿额度

### 每日基础额度

自然日额度按服务器的 Asia/Shanghai 日期记录。基础剩余 = max(0, 当前等级日上限 - 当日已使用基础额度)。午夜换日不依赖“批量清零任务”成功与否，历史记录保留。

普通用户当天已使用 1 次，开通 V1 后基础剩余为 19。当天续费、重复支付通知、切换设备均不清空已用数。会员在当天到期时立即按普通用户上限计算；例如当天已经使用 5 次，剩余为 0，次日恢复普通用户 1 次。

当用户解锁新岗位时，按有效且最早到期的补偿额度优先使用，再使用当日基础额度。页面分别展示“今日剩余”和“补偿可用”，不把补偿伪装成等级升级。

### 数据质量补偿：建议规则

| 项目 | 建议基线 |
| --- | --- |
| 可补偿原因 | 解锁时实际已失效、岗位关键信息错误、同一岗位重复计次；有解锁记录和核验依据 |
| 不自动认定为数据错误 | 解锁后正常招满、用户个人不喜欢岗位、企业未回复投递 |
| 申请入口 | C03 岗位反馈、C18 已查看记录；预填关联解锁事件 |
| 处理时限 | 原型暂展示“预计 2 个工作日内处理”，需运营确认后才能成为正式承诺 |
| 补偿数量 | 每条核实存在问题的解锁事件发放 1 次；重复举报不重复发放 |
| 补偿有效期 | 发放起连续 7 × 24 小时，跨日不清零，会员到期仍可使用 |
| 是否受日上限限制 | 独立于基础日上限；例如基础剩余 0、补偿 1，仍可解锁 1 个新岗位 |
| 扣次关系 | 保留原解锁和原扣次审计记录，追加补偿流水，不同时减少原已用数再额外赠送一次 |
| 补偿额度解锁再次遇到无效岗位 | 按新的解锁事件核验，可补回 1 次，记录完整关联链；不能重复补偿同一事件 |

系统业务失败的额度释放属于纠错，不作为一次额外赠送。退款和数据质量补偿分开处理，避免同一诉求在多个后台入口重复发放权益。

## 5. 有效期、续费与套餐变更

建议每份会员服务持续 30 × 24 小时。服务区间使用 [开始时间, 结束时间)，页面显示具体北京时间。首次开通从服务端核实支付并成功发放权益的时刻开始；付款后因系统异常延迟开通，不扣掉延迟期间的服务时长。

同级续费从现有已付费服务结束时间继续追加 30 天，旧服务剩余时长保留。每份订单有独立服务记录，首次发放确定开始与结束时间后，重复回调不改变这些时间。

第一版购买限制：

1. 无有效会员、无未完成的购买订单时，可以选任意等级。
2. 当前有效会员仅可续费相同等级；跨级购买入口展示说明，不创建支付订单。
3. 未开始且已经付款的续费段也计入套餐校验；不可通过多端下单买到冲突等级。
4. 同一账户同一时刻最多一个待支付会员订单，可继续支付或取消；取消须服务端确认关单结果。
5. 支付时会员状态发生变化，服务端再次核对。任何已付款订单都必须进入明确的发放或退款处理，不能静默丢弃。
6. 真实价格、服务周期变更只影响新订单；已下单的金额和已购买权益按订单快照处理。套餐停卖不取消已购买的服务。

## 6. 支付与开通

首期购买入口为微信小程序。原型使用模拟支付状态，不执行真实扣款。信息查询会员应使用哪一种支付产品、对应系统的购买能力，以及所需主体和类目，仍需接入核验。

流程：选择套餐 → 明确金额/期限/额度/服务说明 → 创建订单 → 调用获准支付能力 → 服务端验证支付结果 → 发放一次会员权益 → 展示开通结果 → 返回原岗位。

支付事实和权益发放分别记录。用户完成付款但发放尚未完成时，显示“已付款，会员开通中”，提供刷新和支持入口；不能把客户端提示成功直接当成会员已生效。

后台必须核对订单、收款方、金额、币种和签名，并处理重复通知、主动查单和对账。订单款项应使用最小货币单位的整数存储。原型中的“补发权益”动作仅针对已经核实收款且未正确发放的订单，不允许直接修改支付事实。

| 异常 | 用户可见状态 | 处理 |
| --- | --- | --- |
| 客户端取消 | 支付未完成 | 保留订单，按服务端状态继续付款或关闭 |
| 支付结果未知 | 结果确认中 | 查单后更新，不自动换单再次扣款 |
| 已付款、发放失败 | 已付款，待处理 | 自动重试或人工核实补发，发放幂等 |
| 已开通后重复通知 | 已开通 | 返回已有结果，不再次延长或重置额度 |
| 当前环境无法购买 | 当前环境暂不支持购买 | 按渠道规则展示，不设计未经核验的绕行支付 |
| 日对账不一致 | 后台异常待处理 | 核实后补发或退款，保留处理记录 |

## 7. 退款与售后

以下为拟议业务处理规则，不是已经发布的退款条款，也不替代实际支付渠道要求。正式销售前，需要确认申请时限、支持范围、退款金额计算与渠道操作方式；这些未定项不妨碍制作模拟原型，但不能留到真实收款后再决定。

| 场景 | 建议处理 |
| --- | --- |
| 未支付订单 | 关闭订单，无退款；关闭前核实支付状态 |
| 已支付、服务尚未开始 | 支持整份服务申请全额退款，渠道成功后取消对应服务段 |
| 已支付且因平台故障持续无法交付 | 人工核实后补交付或退款，记录用户选定的解决方式 |
| 已开始或已使用的服务 | 受理售后申请，展示原因、证据与可申请金额；具体核算政策待定，不自动承诺全退或一律拒绝 |
| 单个岗位数据错误 | 优先按第 4 节补偿；如涉及更广泛服务问题，允许升级售后处理 |

退款过程区分“已申请、审核中、申请未通过、渠道处理中、退款成功、退款失败/异常”。渠道确认成功前不能显示“已退款”。同一订单并发退款需防止超额退款；累计成功及在途退款不得超过可退款金额。

权益调整关联具体订单：待退款服务段暂停新增消费，其他已生效且不受影响的订单保持可用；退款失败或撤销申请后按未消费剩余时长恢复。实际退款成功后移除对应未消费服务段，已开始的段按最终售后决定终止或调整。

第一版同级多份续费采用服务段顺序队列：删除或终止退款段后，从当前时间或仍有效服务段结束时间开始，按原顺序安排后续非退款订单的完整未消费时长，记录调整前后时间。不能直接清空全部会员，也不能损失其他付费订单的剩余时长。

已发生的岗位解锁记录和历史消费不因退款直接删除；建议既有岗位继续免费回看。退款后不刷新基础日额度，当日已用数保留。补偿流水和退款处理需要关联同一售后单，避免重复救济；已使用服务退款的最终范围为待定项。

## 8. 网站与小程序账号共用

内部用户 ID 是会员和额度归属主体。微信登录标识、网站登录凭据只是该用户的登录方式。不能假设不同端的 OpenID 相同，也不能仅凭昵称、头像或未验证的手机号合并账户。

建议网站初期通过经核验可接入的微信账号关联流程绑定小程序用户，界面包含待确认、绑定成功、过期、取消、账号冲突状态；具体方案选择在接入前确定。只在用户完成身份验证和明确关联后共享权益。

用户换设备或退出登录不清空已用次数。两个已有账户产生冲突时进入人工核实，不自动把两份每日额度相加；如果允许合并，按统一岗位去重解锁，并保留当日既有消费、订单和售后链路，另行制定合并规则。

## 10. 验收场景

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| AC01 | 普通用户首次解锁 A，再打开 A，然后解锁 B | A 扣 1，再看 A 不扣，B 提示基础额度不足 |
| AC02 | 次日打开昨天解锁的 A，再首次打开 B | A 不扣，B 消耗今天 1 次 |
| AC03 | V1 当天解锁 20 个不同岗位 | 第 21 个新岗位在无补偿额度时拒绝；旧岗位仍可回看 |
| AC04 | 普通用户当日已用 1，开通 V1 | 当天基础剩余 19，付款与会员信息一致 |
| AC05 | 同一岗位并发打开 5 次、或刷新重试 | 只产生一份解锁权益与一次消费 |
| AC06 | 剩余 1 次，同时解锁两个不同岗位 | 至多一个首次解锁成功，不超扣、不出现负余额 |
| AC07 | 会员到期或跨北京时间午夜 | 按明确服务期限和业务日期计算，已解锁不重复收费 |
| AC08 | 同一付款通知重复到达，或先查单后通知 | 仅发放一份服务，期限与额度不重复增加 |
| AC09 | 已付款但开通失败，之后补发成功 | 用户无需再付款，服务时长不因平台延迟缩水 |
| AC10 | 无效岗位反馈通过，用户跨日使用补偿 | 补偿与基础额度分开，7 天建议有效期内可用，同事件不重复补偿 |
| AC11 | 已有当前会员与两份续费，退其中一份未开始服务 | 仅退关联金额与服务，其他订单剩余时长保留；用户可查看调整结果 |
| AC12 | 同用户从网站和小程序查看同岗位 | 会员、余额、解锁记录一致，不重复扣次 |
| AC13 | 套餐修改价格或停卖 | 已支付订单权益不变，新订单按新版本校验 |
| AC14 | 通过企业页或分享直接打开详情接口 | 与正常入口执行相同解锁规则，不泄露完整受限内容 |

## 11. 业务验证与上线前待定项

闭环包含数据质量、交易履约和持续使用三个方面：

1. 数据质量：采集完成 → 核验发布 → 反馈纠错 → 岗位修正或下架 → 必要补偿。监测来源成功率、重复率、已确认错误解锁比例、核验时间和反馈处理时长。
2. 交易履约：选套餐 → 支付核实 → 发放 → 消费 → 续费/到期/售后 → 对账。监测已支付未开通订单、发放延迟、重复扣次和退款积压。
3. 持续使用：用户首次有效解锁 → 回访查看新岗位 → 购买与续费。监测首次解锁转化、额度耗尽情况、各等级日使用分布、再次访问、付费转化、续费及维护成本。点击投递链接不能当作实际投递成功或录用。

- 三档价格及是否采纳 30 天方案。
